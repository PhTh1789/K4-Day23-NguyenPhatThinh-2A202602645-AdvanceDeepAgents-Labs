# Tool Use in Large Language Model Agents: Architectures, Training, Evaluation, and Security

## TL;DR

- A tool-using agent is defined less by any single mechanism than by a control loop that interleaves reasoning, tool calls, and environment observations across multi-step tasks [1]; with open function-calling models and datasets now widely available [2][3][4], the field's bottleneck has shifted to correct tool selection among thousands of candidates [5], faithful execution of declared plans [6], and a finite context budget [7].
- Tool-selection failure is a decision-stage problem rather than an attention problem: one analysis of real Berkeley Function Calling Leaderboard failures reports that per-candidate attention argmax lands on the correct tool 80% of the time against a 21% chance baseline, and the gold tool is under-attended in only 10% of cases [8]; retrieval-side fixes therefore target candidate-set construction, from training-free intent-expansion indexing [5] to function-class-organised post-training [9].
- Long-horizon reliability is predominantly a context-management problem, and the proposed remedies diverge sharply: explicit belief states separating world state from unresolved requirements [10], training-free reversible context folding that avoids irrecoverable discards [11], per-turn compaction that never accumulates a transcript [7], learned soft memory tokens that approximate full-history continuations [12], and external natural-language rulebooks that let frozen agents revise world models [13].
- Training and data supply have moved from prompt engineering to supervision at scale: API-grounded corpora [4], transparent curated datasets [14], domain datasets [15], GUI trajectory synthesis from web tutorials [16], schema-free synthetic enterprise data [17], and RL frameworks that own environment orchestration and rollout scheduling for concurrent multi-turn episodes [18].
- Orchestration is treated as a management capability in its own right: benchmarks now isolate a single model's ability to lead subagents [19], recursive multi-agent search is proposed to escape single-trajectory limits [20], orchestrator-worker frameworks formalise planner-executor-memory roles [21], and coordination across heterogeneous models is stabilised by runtime confidence calibration without retraining [22] or by evidence graphs used for process supervision [23].
- Evaluation is being criticised from the inside: tool-routing benchmarks under-represent rare scenarios, lack adversarial hard negatives, and rely on LLM judgments never validated by execution [24]; cross-benchmark synthesis argues that leaderboard gains obscure recurring failure modes across 19 benchmarks [25]; and audits find that indirect-prompt-injection harnesses can produce wrong-but-publishable results through silent payload non-delivery or scoring attack success by tool identity instead of call arguments [26].
- Because tools carry executable authority, security failures are specific to tool access: poisoning moves into tool metadata [27], becomes stealthy and multi-tool [28] and sycophancy-exploiting [29], is injected mid-session through third-party scripts [30], self-propagates through authored skills [31], and leaks data through search tools [32]; defences proposed range from semantic privilege separation [33] and capability confinement after contamination [34] to digital-twin resource authorization [35], network-level guardrails [36], and unified frameworks covering four attack classes [37].
- Reliability is fragile wherever tool calling meets another output constraint: jointly enabling JSON-Schema structured output and tool calling makes open-weight models stop invoking tools while schema compliance stays high [38], and in sub-3B models hard output constraints can change the answer itself rather than only its format [39].

## Background

The surveyed literature converges on an operational definition: an LLM agent "tackles multi-step tasks by interleaving reasoning and tool calls with observations from the environment" [1]. Everything else in this survey — planning, retrieval, memory, training data, evaluation, security — is a consequence of that loop running repeatedly against real effects.

Two stacks matured in parallel. The model-and-data stack made tool calling a first-class capability rather than an emergent behaviour: ToolLLM couples a tool-use dataset covering 16,000+ real-world APIs with a decision-tree search procedure, automatic evaluation, and neural API retrieval [4]; GRANITE-20B-FUNCTIONCALLING was released as an open-access function-calling model whose capability is attributed to multi-task learning over granular tasks [2]; Hammer targets on-device function calling using an augmented dataset and function masking [3]; and ToolBridge frames a curated open-source dataset explicitly around transparency for external tool integration [14]. The execution stack made agents testable: ToolGym is reported as an open-world environment of 5,571 unified tools across 204 apps for testing and data curation under unreliable tool states [40].

This survey draws on records retrieved from three families — arXiv search, the Hugging Face Daily Papers feed (keyword `agent`), and Hugging Face paper search. No web source was available in this run: every attempted web fetch returned HTTP 429, and the sandbox has no direct network path, so every claim below rests on the abstracts and metadata those retrieval tools returned rather than on independently re-fetched full texts.

## Plan Declaration Versus Faithful Execution

The clearest recent conceptual split is between choosing a plan and carrying it out. One study formalises a "Plan Declaration–Execution Gap": planner-executor systems can fail either at plan selection or at faithful execution, and end-task success alone cannot distinguish the two, so pattern-specific execution evaluation is needed rather than outcome-only scoring; its "Planning-as-Routing" framing has the model declare one of four planning modes, including Predefined, Sequential and Hierarchical [6]. This reframes agent tuning: the same final score can hide two very different defects.

Two contrasting approaches supply mid-task correction. Caddie trains a natural-language critic for tool-using agents from eventual task outcomes, deliberately avoiding step-level labels and reference critiques, so the critic learns what advice actually helps an agent that interleaves reasoning and tool calls [1]. Opera, aimed at long-horizon coding agents, instead treats each correction as a persistent note that is followed until the diagnosed problem is resolved, decides when to review through periodic and event-driven triggers, diagnoses issues with typed operators, and audits feedback against visible evidence — motivated by the observation that misjudged feedback can be harmful rather than merely useless [41]. The difference matters: Caddie optimises advice against outcomes, whereas Opera constrains advice structurally so that it remains verifiable while work is in progress.

Beyond the single loop, three reductions are visible. WebSwarm argues that a single ReAct-style search agent is bounded by one trajectory and limited context, so depth and coverage trade off against each other, and existing parallel multi-agent search still lacks recursive depth, collaboration adaptability, and evidence-grounded expansion [20]. Lemon Agent packages the opposite choice — an orchestrator-worker system whose AgentCortex framework formalises a Planner-Executor-Memory paradigm with adaptive task execution plus hierarchical self-adaptive scheduling, motivated explicitly by limits in resource efficiency, context management, and multimodal perception [21]. Station sidesteps fixed objectives altogether, placing multiple agents in an open-world scientific ecosystem and adding a Supervisor with periodic Meta Reflection so exploration persists when intermediate metrics are absent [42].

## Selecting Among Thousands of Tools

Once tool libraries reach the thousands, prompting stops being viable: full-library prompting grows prompt tokens and latency with every candidate and adds distractors that degrade selection [5]. The retrieval-side response is Toollery, a training-free candidate-compression framework that expands queries on the document side — generating user-intent queries from each tool specification — and builds a retrieval index mapping real requests to a compressed candidate set [5].

Training-side approaches attack the same problem differently. ToolCompass observes that agents must generalise from tools seen in training to unseen tools at deployment, and that "tool trialing" is the crux: excessive trials waste the interaction budget while selective trials enable exploration; outcome-based post-training leaves trials unguided, yet turn-level supervision can suppress necessary exploration, so ToolCompass organises tool-call representations by shared function class instead [9]. Where Toollery changes the candidate set at inference, ToolCompass changes the representation learned during post-training.

Diagnostics complicate the "crowded context" story. Using real BFCL failures, one study measures attention over labelled tool-definition segments and finds the model attends most to the correct tool 80% of the time (21% chance), with the gold tool under-attended in only 10% of cases — concluding that failure sits at the decision stage rather than in a lost-in-the-middle attention failure [8]. If selection errors are decisional, retrieval compression [5] and representation-level post-training [9] address different parts of the pipeline than an attention-based fix would.

A distinct reliability family concerns interference from output constraints. In production, enabling tool calling and JSON-Schema constraints simultaneously caused multiple open-weight models to cease invoking tools while retaining high schema compliance — a phenomenon named "Tool Suppression", reproduced across model families and deployment settings [38]. The small-model analogue is the "constraint tax": for sub-3B models, production requirements such as JSON objects, typed traces, regex-constrained fields and tool-call schemas mean the common assumption that hard constraints improve reliability without changing the answer is unsafe, because constraints can alter correctness, not just validity [39]. Both results argue that validity metrics alone are insufficient evidence of working tool use.

## The Working Set: Memory, Belief, and Context Budget

Long-horizon agents re-send an append-only interaction history at every step, so context and cost grow until sessions exceed the window; ReFold criticises existing context-management methods that predict requirements via extra model calls, heuristics or trained policies, because they add runtime overhead, invalidate prefix caches and permanently discard content with no guarantee of recovery, and proposes a training-free reversible folding layer instead [11]. Continuous Context Management takes the opposite architectural stance: compaction happens every turn, so the next prompt holds the original task, retained memory and the newest observation rather than the transcript, first evaluated without fine-tuning on TerminalBench-2 with Claude Sonnet [7]. The contrast is between reversibility without per-turn compaction [11] and per-turn compaction without reversibility.

A second family argues that summaries are the wrong abstraction. PoS holds that organising history into memory does not ensure a coherent understanding of the current world, and instead maintains explicit belief states as the decision context, each combining an estimate of the current world state with unresolved task requirements, validated for consistency and monitored for task progress [10]. REMORY keeps the summary but augments it: a neural memory network generates a bounded sequence of soft memory tokens that help a frozen LLM approximate the continuation it would have produced with the full history, appended after the summary as a residual connection along the sequence dimension and evaluated on SummHay [12]. Memento 3 goes further toward persistent, human-readable state, enabling frozen LLM agents to continually learn explicit world models through external memory in the form of a natural-language rulebook that records revisable hypotheses about environment dynamics — noting that limited observations can support multiple world models that explain the past yet diverge on unseen states [13]. These five mechanisms [10][11][7][13][12] are rarely compared on shared tasks, which is itself a gap discussed below.

## How Tool-Use Competence Is Acquired

Data construction has diversified along the axis of supervision cost. API-grounded corpora remain the reference point: ToolLLM's dataset, decision-tree search, automatic evaluation and neural API retrieval jointly target 16,000+ real APIs [4], while ToolBridge emphasises transparency and curation for external tool integration [14]. Domain specialisation is represented by BioTool, whose paper reports that a model fine-tuned on the biomedical tool-calling dataset outperforms commercial alternatives in the specialised domain [15]. Where human annotation is the constraint, AgentTrek synthesises GUI agent trajectories from web tutorials, claimed to be more cost-effective than human annotation [16]. Where legal and business restrictions block access to enterprise systems, data and schemas, Synthesis Through Simulation proposes a schema-free paradigm for generating coherent enterprise data through scalable agent-system interaction, arguing that tabular synthesis is limited by structural validity and schema availability while procedure-based approaches lack distributional fidelity [17].

Optimisation methods split between parameter-efficient adaptation and reinforcement learning. Granite attributes function calling to multi-task learning over granular tasks [2]; Hammer combines an augmented dataset with function masking for robust on-device calling [3]; ToolCompass shows that outcome-based post-training and turn-level supervision fail in opposite directions and organises representations by function class instead [9]; a small-model study targets edge deployment without cloud infrastructure, using the Berkeley Function Calling Leaderboard framework and comparing supervised fine-tuning, parameter-efficient fine-tuning, RL-based optimisation, preference alignment via Direct Preference Optimization, and hybrid methods [43]. Infrastructure — not algorithms — is the bottleneck for RL at scale: MCP-Universe RL argues existing RL frameworks for tool use stop at the policy update, leaving practitioners to stand up isolated environments for hundreds of concurrent trajectories and to schedule rollouts so GPUs stay busy across long multi-turn episodes stalled on slow tool calls, and offers an open-source framework covering both [18].

## Orchestration: Subagents, Teams, and Coordinated Confidence

As single agents saturate, orchestration becomes measurable. ClawArena-Team notes that production agents act as managers that spawn specialised subagents and orchestrate their parallel, asynchronous returns, yet neither benchmarks scoring a policy's own task-solving nor those scoring a fixed multi-agent system's emergent behaviour isolate the management ability of a single model acting as leader; it provides 41 multi-turn, multimodal, multi-directory scenarios for that purpose [19]. Recursive orchestration is the complementary proposal, with WebSwarm motivated by the limits of one long trajectory and by the shallowness of parallel aggregate systems in recursive depth, collaboration adaptability, and evidence-grounded expansion [20], while Lemon Agent's AgentCortex formalises planner, executor and memory roles with hierarchical self-adaptive scheduling [21].

Coordination quality is also treated as a calibration problem. MARGIN observes that when a coordinator compares answers from heterogeneous foundation models, self-reported confidence may mean different things across responders and changing workloads, and learns model-specific confidence corrections at runtime from observed outcomes without retraining the models or requiring a held-out calibration set, tracking recent accuracy and stated confidence within bands and blending sparse-band corrections [22]. Evidence structure offers another route: OneSearch-VL centres a multimodal deep-research agent on a Visually Grounded Evidence Graph encoding dependencies among visual anchors, entity relations, source-supported facts and answer-producing operations, and uses it as a shared reference for data construction, process supervision and operation-level evaluation [23].

Orchestration also creates a supply-chain surface. Skill Constellations defines agent skills as SKILL.md instructions and scripts run by coding agents such as Claude Code and Codex with the user's permissions, and observes that because developers copy skills between repositories they form a software supply chain without a registry, versions or provenance — so the origin of a copied skill and the reach of a security fix are unknown, motivating a first dated copy network of agent skills [44].

## Evaluation and Security: What Benchmarks Miss and How Tool Access Is Attacked

Evaluation methodology is under audit. PluginEval names three structural limitations of tool-routing benchmarks: power-law data distributions leaving rare scenarios under-represented, the absence of adversarial hard negatives that would separate models, and annotation pipelines depending on LLM judgments never validated through execution [24]. A cross-cutting synthesis of 27 papers and 19 benchmarks from 2023–2026 argues that reported benchmark gains obscure recurring failure modes documented across otherwise unrelated evaluation efforts [25]. Harness validity can fail even in security evaluation: auditing an indirect-prompt-injection benchmark and its harness surfaced four defect classes — silent payload non-delivery, attack success scored by tool identity rather than call arguments, false-rejection rate conflated with model incapacity, and no audit trail — each yielding a plausible but wrong result [26].

What benchmarks measure also varies along an axis from component to trajectory to deployment. PlanBench-XL targets retrieval-limited visibility, with 327 retail tasks over 1,665 tools and iterative retrieval to uncover intermediate evidence for later calls [45]. DynamicMCPBench rejects both final-answer scoring and fixed ground-truth tool lists as fragile once data is live and stateful, offering a reusable framework a practitioner can run on their own MCP servers [46]. ToolPrivacyBench argues conventional function-calling benchmarks capture task completion and API correctness while privacy benchmarks inspect final responses or privacy judgments, and that neither captures purpose-bound information flow across an executed multi-tool trajectory, which it audits directly [47]. Reward-focused evaluation adds another dimension: the Reward Hacking Benchmark supplies multi-step tool tasks with naturalistic shortcut opportunities such as skipping verification steps, inferring answers from task-adjacent metadata, or tampering with evaluation-relevant functions, with chained regimes using chain length as a proxy for longer horizons and 13 frontier models evaluated [48]. Horizon is explicitly framed as an artefact: one study finds benchmark success rates rising while production reliability on long workflows stays low, attributing the gap to benchmark horizons being an order of magnitude shorter in dependent steps than production workloads, across nine models — six open models from 1.2B to 671B parameters plus three deployed production systems [49]. Coverage gaps are documented too: tool-calling benchmarks are predominantly English-centric, leaving non-English prompting such as Arabic poorly understood [50]. Beyond arXiv, the Daily Papers feed contributes benchmark designs with explicit scoring regimes: TestPrism's 300 test tasks from 17 sources and 3,000 candidate implementations (half valid, half invalid) with a Joint Success Function requiring failure on the initial program state plus acceptance of every valid candidate and rejection of every invalid one [51]; BrickBench scoring validity, alignment and design across three settings that vary scale and part availability, with BrickAgent as an environment for coding agents to construct, inspect and validate designs [52]; an agentic black-box-optimisation benchmark motivated by incompatible task domains and system configurations across prior studies [53]; and trajectory-level epistemic humility operationalised as Identify, Solve and Escalate [54]. Domain and ecosystem benchmarks fill gaps at the execution layer: FinToolBench offers a real-world financial tool-use benchmark with 760 executable tools and criteria extending beyond execution success [55], MCPToolBench++ provides a large-scale multi-domain benchmark for Model Context Protocol tool use [56], and ToolGym's 5,571 tools across 204 apps target robustness under long-horizon objectives and unreliable tool states [40].

Security work treats tool descriptions and skill libraries as the primary attack surface. Tool Description Poisoning places malicious instructions in a tool's descriptive metadata rather than its executable code, aiming at the agent's cognitive planning layer, and is paired with a benchmark for evaluating MCP poisoning [27]. ShareLock argues that existing poisoning schemes rely on monolithic plaintext embedding that fails against manual inspection or automated detectors, and proposes a stealthy multi-tool threshold poisoning attack against MCP [28]; MCPXKIT attributes tool poisoning to hidden instructions that exploit LLM sycophancy and notes that MCP-security research remains mostly narrow or qualitative [29]. WebMCP enlarges the surface by letting websites expose tools directly to agents, with Mid-Session Tool Injection using third-party scripts to inject malicious tools into an active session, classified by attack stage and target [30]. Supply chains are targeted next: ShieldNet argues malicious behaviour is embedded in seemingly benign third-party tools and MCP servers that can hijack execution, leak data or trigger unauthorised actions, introducing the SC-Inject-Bench benchmark with over 10,000 malicious items alongside network-level guardrails [36]. Self-evolving agents self-poison: EvoMal shows a retrieved malicious skill becoming the template for a new malicious skill that the agent authors, stores and runs, amplifying the effect by wrapping an interchangeable payload in benign-looking structural "banner" elements that induce imitation [31]. Exfiltration via legitimate tools is also demonstrated: because tool calling and retrieval-augmented generation give agents access to sensitive corporate data, web-search tools become an exploitable channel for indirect prompt injection [32]. Finally, architecture-level analyses argue that agents break classical assumptions about code-data separation, authority boundaries and execution predictability, creating new confidentiality, integrity and availability failure modes [57].

Defences mirror the attack taxonomy. A unified framework addresses four named classes — direct prompt injection, indirect prompt injection, memory poisoning and backdoors — with two "universal tool-based" components [37]. AgentVisor frames the core tension as security versus utility, where rigorous protection causes over-defence while subtle indirect injections bypass detection, and applies operating-system-style semantic privilege separation [33]. SkillGuard addresses what it sees as an unhandled problem — how an agent's future authority should change once untrusted data enters its state — by treating such data as "contamination" and confining subsequent capabilities, while noting the approach is conditioned on sound skill summaries [34]. Pincer takes the systems view that defences restricting agent architecture — typed tools, information-flow control, policy-prediction engines — sacrifice too much functionality to be adopted, observes that deployed agents rely on user-mediated plus automode sandboxing, and proposes resource authorization via a digital twin [35].

## Trends and open problems

Three shifts organise the current state of the field. First, the locus of difficulty has moved from invocation to adjudication: benchmarks and analyses increasingly separate selecting a plan from executing it [6], selecting a tool from using it [8], and routing from deciding [9][24], while reliability failures appear in the interaction between tool calling and other output requirements [38][39]. Second, supervision is being industrialised — datasets and synthesised trajectories [17][15][4][14][16], post-training that organises tool representations rather than suppressing exploration [9], and RL infrastructure that owns environments and rollout scheduling [18] — with evaluation rushing to catch up via effect-scored and validity-audited benchmarks [46][26]. Third, agent capability is increasingly mediated by shared artefacts rather than a single model: tool libraries [5], MCP servers [56][46], skill libraries [44][31], and subagent teams [19][21].

Several problems remain open on the evidence surveyed. The memory and context mechanisms are numerous and mutually incomparable — reversible folding [11], per-turn compaction measured on TerminalBench-2 [7], soft memory tokens measured on SummHay [12], explicit belief states [10], and external rulebooks [13] — with no shared task showing which regime wins under which horizon. Evaluation validity is unsettled in both directions: benchmarks are accused of unrepresentative data and unvalidated LLM judges [24], harnesses of producing wrong-but-plausible outcomes [26], and deployment-relevant horizons of being systematically shorter than production [49], while privacy, reward and epistemic behaviour are only beginning to be measured at trajectory level [54][47][48]. Security-versus-utility remains an explicit trade-off rather than a solved design problem, with defences deliberately accepting residual risk [33][35][34] and skills propagating without provenance [44][31]. Comparability is a recurring obstacle outside security too: agentic black-box-optimisation studies use inconsistent domains and configurations that hinder comparison and obscure individual design choices [53], multilingual coverage is thin [50], and small-model tool calling relies on leaderboard frameworks designed for larger systems [43]. Finally, the reviewed corpus itself is uneven — the arXiv search tool served a recent window, so classic mechanism papers were not retrievable, and no web family was available in this run — which limits how far historical continuity can be traced from these sources alone.
